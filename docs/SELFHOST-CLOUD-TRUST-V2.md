# Self-host, Cloud pilot and Trust Pass v2 operations

## Deployment boundary

Self-host has no Cloud SDK, entitlement server, subscription or telemetry dependency. Serve the versioned `public/bicaptcha.js` built with this app. Logging remains off by default. Cloud is a separate deployment/key/deployment-ID/database/Redis namespace and selects `BICAPTCHA_MODE=cloud`; self-host selects `selfhost`. Never share signing keys or deployment IDs. No license has been assigned; vendor/solver files are neither deleted nor included in the Docker build context. No Cloudflare/crypto/payment integration exists.

1. Install Node 22.18+, npm, Docker Compose. Run `npm ci && npm run db:generate`. Prisma 5.22 commands are used, not newer Prisma 7/8 migration commands. SQLite migrations stay in `prisma/migrations`; **only** `npm run db:deploy:postgres` targets `prisma/postgres/schema.prisma`. The raw SQL security tables are intentionally managed by that migration, not Prisma models: never run `db push`, `migrate dev` or a generated schema diff against this production database.
2. Copy `deploy/production.env.example` to `.env.production` outside source distribution and populate independent random keys/passwords, exact HTTPS `APP_ORIGIN`, deployment ID and mode. Supply `POSTGRES_PASSWORD`/`REDIS_PASSWORD` to Compose from an operator secret manager/environment; percent-encode URL credentials. Redis runs AOF/appendfsync-always/noeviction with the password provided as one quoted process argument over an internal-only network. No real secrets are shipped. Back up these operator files separately and never add them to the Docker build context.
3. Install real TLS files at `deploy/tls/fullchain.pem` and `privkey.pem` with restrictive permissions. Review host/firewall boundaries. Run `docker compose build`, `docker compose up -d postgres redis`, then **for an empty intended Postgres only** `docker compose run --rm app npm run db:deploy:postgres`. Finally `docker compose up -d`. These are operator instructions, not commands performed on a live installation in this task.
4. `/api/health/live` is process liveness. `/api/health/ready` requires production config, Redis access and the durable ledger. Ingress waits for app readiness. Only ingress publishes port 443; app has no published port and state network is internal. The compose ingress strips Forwarded/XFF/real-IP/Cloudflare headers and sets the TLS protocol itself. App code **ignores all IP forwarding headers**; the env ingress contract is not an IP authentication flag. Do not add an origin port or another ingress to these networks. Network policy/firewall review and actual TLS deployment remain operator gates.
5. Use durable Postgres backups with restore drills, Redis AOF/noeviction and NTP on all nodes. Availability requires tuned upstream and site/account/credential limits; current conservative defaults are not a load-tested SLA. Redis errors/timeouts return 503 without a memory fallback. Metrics retention is separate from receipts: do not prune consumption receipts/audit/usage using the analytics cleanup job. Expired nonce/challenge rows may be purged by a reviewed offline retention job; never restore replay state to an earlier point.

## SQLite export/import is a separate approval

No migration is run on `prisma/dev.db`. Before any transition, stop writes in a maintenance window, make an offline read-consistent SQLite backup (or SQLite backup API), hash it and restore-test a copy. Inventory canonical-domain/email collisions and counts for User/Site/ValidationLog and legacy credentials. Dry-run export from the **copy** into a new, empty Postgres baseline preserving IDs, timestamps, ownership, verification status and credential hashes (never promote unverified sites). Old plaintext `secretKey` values remain unusable; owners should rotate credentials. Validate source/destination row counts, every relation, duplicate/unique constraints, timestamp conversion, exact domain policy and per-owner samples, then run security tests with production-shaped config. Record a signed operator approval before cutover. This release does not silently export/import, reset or rewrite user data. On errors retain maintenance; do not restore old receipts or legacy bypass code to resume traffic.

## Consumption and billing contract

Redis owns challenge single-use and rate-limit windows. Signed production tokens bind deployment/site/action/exact hostname and expire in 120 seconds. After signature/context/site/credential checks, Postgres inserts a unique `(deployment,tenant,site,jti)` receipt and increments usage within the **same transaction**. No cross-store atomicity is claimed. Losing an issuance response may waste a challenge. Losing a response after DB commit means the first consumption can already be billed: the retry is rejected, never a new authorization or charge. An uncertain COMMIT outcome must fail closed. Customer business-side effects still need their own idempotency key.

Cloud Pro is an **administrator-approved time-limited pilot**, not purchased service. No tax, charge, webhook or payment success is fabricated. Base estimate is 19,990,000 microUSD/month; included first successful backend consumptions are 100,000/UTC calendar period. Additional units cost 990 microUSD. Period total is rounded once to cents, half-up. Challenge issuance, failure, retry and replay do not increment usage. Overage defaults off; owner consent plus a strictly positive **additional** microUSD cap is mandatory. Next use is rejected with 429 if quota/cap would be exceeded; no successful token-consumption response is emitted. Disabling overage/lowering a cap never erases prior usage. Dashboard warns at 90,000. Price estimates are not charges or invoices. Basic features are not invented; Enterprise points to https://developer.org.tr/contact.

`/api/cloud` is session-authenticated and writes require exact-Origin CSRF protection. POST operations: `create {name}`; owner-only `attach-site {org,site}`, `add-member/remove-member {org,account}`, `overage {org,enabled,capMicroUSD}`. Site attachment requires both org owner role and existing Site user ownership; no silent reassignment. Members can read pilot status, not change it. Only server-provisioned account IDs in `BICAPTCHA_ADMIN_IDS` may `approve {org,ends}` (future ISO UTC time, at most 31 days) or `revoke {org}`. No default administrator/self-promotion endpoint exists. Approval/extension preserves usage/consent. Current UTC periods advance without resetting historical rows. Each mutation leaves an audit event without credentials or proof payloads. Configure admin IDs outside the browser after reviewing account identity. Cross-deployment Cloud calls are never required by self-host.

## Trust Pass v2

Legacy `/api/bi-captcha/register-pass` stays 410 and legacy `extension/manifest.json` stays disabled. Only the new v2 package and `/api/trust/v2/{control,pass}` participate. Server compatibility: app 0.2.x, extension 2.0.0. Optional SDK flag `trustPassV2: true` tries the extension, then boundedly falls back to normal CAPTCHA. Final success tokens still require backend siteverify and normal Cloud metering.

1. Generate an explicit unpacked package with `npm run package:extension -- /absolute/operator-extension-config.json /absolute/output`, where config is `{ "origin":"https://captcha.example.com", "deployment":"unique-deployment-id", "origins":["https://shop.example.com"] }`. No wildcard origins. Only the deployment has required host permission; listed customer origins are optional and content scripts are registered only after user permission. No externally_connectable or web sign-message endpoint exists. The private P-256 CryptoKey is generated non-exportable in the extension service worker and stored in extension IndexedDB, never returned to pages or the popup. Popup exposes only its public key.
2. Log into the dashboard, expand deployment controls, copy the public key, and specify verified site key, explicit action and exact hostname. First passkey registration additionally requires the current account password, so a stolen session alone cannot bootstrap a new authenticator. Confirm the scope and complete WebAuthn UV. Renewal uses an existing account credential with fresh UV. Challenge has 120-second lifetime and its server binding includes the public key/account/deployment/scope. The transaction atomically consumes the challenge, stores/updates the credential and creates the device/grant. New key/scope values cannot be substituted in the finish request.
3. Copy the returned grant config into the extension popup, review its explicit scope, approve optional origin access and enable. Reload the permitted page after dynamic content-script registration. Every pass uses a random one-use 30-second server nonce and P-256 possession signature over the fixed v2 audience/deployment/grant/nonce/site/action/hostname tuple. Page messages provide no authoritative site/action: background picks the unique approved context for the exact sender origin, requires top frame and validates sender ID/origin/tab and bounded payload. No arbitrary string can be signed. Ambiguous multiple contexts for one host are refused rather than guessed.
4. The server verifies registered device key, nonce/context, entitlement, expiry/revocation and budget under durable transaction locks. Grants are limited to 900 seconds/20 uses; env settings may **only narrow** them. Per-site grant use is also capped. CryptoKey possession is not humanity proof. A malicious allowed site can spend the short scoped budget; the permission screen, short TTL/quota and disable/revoke controls limit, not eliminate, that risk. Server failures never produce automatic success.
5. Popup disable removes local active grant and content scripts immediately. Dashboard revoke-all and logout revoke account grants; authenticated control API `revoke {kind:'account'|'device'|'grant', id?}` supports narrower server revocation. Grants/keys from the old protocol are not accepted. Credentials that report zero counters (including synchronized passkeys) are accepted only under library verification policy; nonzero counters must increase, updates are locked. Backup flags are recorded, not treated as hardware/person attestations. Cross-origin frames/topOrigin assertions are refused. Real browser WebAuthn/MV3 testing is still a release gate; generated authenticator fixture tests are not physical hardware/biometric E2E evidence.

## Signed updater (separate operator process)

There is **no live release registry, signing root or deployment key in this repository**. `deploy/updater.example.json` defaults off and contains intentionally unusable paths/origins. The CLI is `npm run update:selfhost -- /absolute/config.json [--approve]`. It is never invoked from a web route, and no Docker socket/root endpoint is exposed to the dashboard.

The modes are `off` (also default when omitted), `notify`, `download-approve`, `auto-security`. Stable channel only; optional exact version `pin`; UTC hour maintenance window `[start,end)`; manual approval via `--approve` for download-approve. Auto-security permits only a higher patch within the same major/minor and a signed security/nonbreaking classification. Schema incompatibility is always rejected. Signed manifest envelope is `{payload:base64url(JSON),signature:base64url(Ed25519(payload-as-ASCII))}`. JSON includes version `X.Y.Z`, monotonic sequence, channel, expiry, artifact URL, sha256, exact size, schema range, security/breaking flags, `imageRepository` and `imagePlatform` (`linux/amd64` or `linux/arm64`). The artifact is a Docker image archive, not arbitrary executable content. Public trust root must be independently reviewed.

Both manifest/artifact are exact-allowlisted HTTPS origin paths. No credentials/query/hash/encoded traversal/commands/redirects or IP literals. DNS resolution is pinned per connection and private/mixed/IPv6 destinations are refused (strict IPv4 public publication policy). Response size, connection and whole-download deadlines are bounded. Artifact size/digest must match; it is staged under a server-chosen digest filename and **not extracted** by this CLI. Root rotation is a manual reviewed procedure: independently verify the new root fingerprint over an established channel, archive old/new root provenance, stop updater, replace the operator-owned root file, preserve sequence/current state, test known signatures, then re-enable. A manifest cannot authorize its own new root.

Operator state starts as `{ "sequence":0,"current":"0.2.0" }`, writable only by the updater owner. A filesystem lock excludes concurrent CLI instances. Installation reserves sequence before mutation and requires a restore-tested backup receipt no older than seven days. The staged file type/mode/size/hash is verified again. The fixed helper runs `docker image load --input <exact file>`, inspects the exact image ref, OCI version label and platform, stops ingress, atomically persists the selected tag in the operator-owned `.env.updater`, updates only app with Compose `--no-build --pull never --no-deps`, checks health, then restores ingress. Failure attempts the prior tag and restores ingress only when healthy; otherwise ingress remains stopped. It never performs DB migrations or rolls back data; schema must stay backward-compatible. Compose paths/repository/platform/backup receipt are operator-owned config. No Docker socket is exposed to the web container.

For subsequent manual Compose operations and host startup automation, always pass `--env-file .env.updater` (for example, `docker compose --env-file .env.updater up -d`); otherwise Compose may select its default image instead of the persisted release. Keep this file operator-owned and backed up with deployment configuration.

The helper passed a throwaway local Compose test that applied a healthy image, verified that a separate Compose invocation resolved the persisted tag, and rolled an unhealthy candidate back to the prior healthy app. This is not a production deployment or real signed-release test. Docker daemon parses the signed image archive; the application does not extract its members. Production use still requires an actual signed release artifact/root, provisioned restore-tested backup receipt and operator review. No production deployment was performed.
